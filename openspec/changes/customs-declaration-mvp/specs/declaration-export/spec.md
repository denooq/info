# Spec Delta

## Purpose

Создавать согласованные PDF ДТ и XML ДТ/ДТС из одной подтверждённой версии данных с явной областью проверки формата и без имитации регистрации в таможенной системе.

## ADDED Requirements

### Requirement: Generate every output from one confirmed revision
Система MUST формировать PDF и оба XML только из одной неизменяемой подтверждённой версии исходных данных, расчётов и правил, без повторного AI-извлечения при генерации.

#### Scenario: Confirmed export bundle
- **WHEN** пользователь подтверждает корректную версию и нажимает «Создать»
- **THEN** PDF, XML ДТ и XML ДТС используют одни и те же товары, документы, выбранные значения, расходы и итоги
- **AND** временное состояние интерфейса не меняет один формат отдельно от остальных

### Requirement: Invalidate stale artifacts
Изменение данных после подтверждения MUST отменять актуальность подтверждения, расчётов и выходных файлов; скачивание как актуального комплекта SHALL требовать нового пересчёта и создания.

#### Scenario: Edit while a generation job is running
- **WHEN** во время генерации пользователь меняет исходные данные
- **THEN** результат старой версии не публикуется как результат новой и не смешивается с её файлами

### Requirement: Publish complete bundles atomically
Система SHALL открывать скачивание только после успешной генерации и проверки всех трёх файлов; ошибка одного файла MUST сохранять подтверждённые данные для повторной генерации без смешения версий.

#### Scenario: DTS generation fails
- **WHEN** PDF и ДТ созданы, но генерация или проверка ДТС завершилась ошибкой
- **THEN** неполный комплект не выдаётся как успешный результат и пользователь видит конкретную причину

### Requirement: Render the declaration PDF programmatically
PDF MUST содержать ДТ с её графами, необходимыми добавочными листами и продолжениями, читаемыми кириллическими шрифтами и полным содержимым полей; система MUST формировать заполнение программно вместо использования изображения готового примера с данными.

#### Scenario: Long goods description or document list
- **WHEN** описание товара или список графы 44 не помещается в основной графе
- **THEN** текст переносится в связанное продолжение без обрезания и наложения
- **AND** значения и коды представления документов совпадают с XML текущей версии

#### Scenario: Several goods need additional sheets
- **WHEN** декларация содержит пять товаров
- **THEN** PDF содержит основной и необходимые добавочные листы для всех товаров
- **AND** графа 3 учитывает листы ДТ, а не все физические страницы PDF с продолжениями

### Requirement: Generate the sample-based XML profiles
Система SHALL создавать XML ДТ и ДТС-1 в отдельных версионируемых профилях на основе `S116510021328.xml` и `DTS_20261105121051096.xml`, сохраняя соответствующие пространства имён и связи товаров без унификации разных версий общих типов.

#### Scenario: Goods references remain consistent
- **WHEN** формируются документы для нескольких товаров
- **THEN** товары ДТ, ДТС и расширения оболочки используют согласованные номера и значения текущей версии
- **AND** отсутствующие в исходном примере ветви не заполняются выдуманными элементами

### Requirement: Validate the sample profile without claiming XSD conformity
Перед публикацией система MUST проверять синтаксис XML, локально закреплённые пространства имён, наблюдаемый порядок и структуру элементов, обязательные значения и межфайловую согласованность. Официальная XSD-проверка отложена по решению пользователя и SHALL NOT блокировать поддержанный образцами случай. Статус MUST явно отличать локальную проверку от официальной XSD и импорта Keden.

#### Scenario: Official schemas are unavailable
- **WHEN** поддержанный случай соответствует локальному профилю, но официальных XSD нет
- **THEN** система создаёт комплект со статусом «профиль примера проверен; XSD не выполнялась»
- **AND** отсутствие XSD само по себе не блокирует скачивание

#### Scenario: Required branch is absent in the sample
- **WHEN** заполненные данные требуют вычета ДТС либо другой ветки, структура которой отсутствует в XML-образце
- **THEN** создание комплекта блокируется с конкретным полем и объяснением ограничения
- **AND** расчёт и редактирование сохраняются; неизвестные элементы не выдумываются

### Requirement: Keep Keden validation scope explicit
Система MUST проверять оболочку и расширения по локальному профилю отдельно и не заявлять совместимость, принятие или успешный импорт в Keden без точного формата и отдельной проверки.

#### Scenario: Only the sample format is available
- **WHEN** комплект прошёл проверки профиля примера
- **THEN** статус не утверждает прохождение XSD ЕАЭС или Keden
- **AND** сгенерированные UUID являются техническими идентификаторами текущего комплекта

### Requirement: Never fabricate registration, release or signature facts
Система MUST исключать автоматическое присвоение таможенного регистрационного номера, статуса выпуска, служебных отметок, сведений об ЭП и идентификаторов готовых деклараций; собственные технические идентификаторы SHALL отличаться от регистрационных.

#### Scenario: Example contains issued identifiers
- **WHEN** шаблонный пример содержит номер `55411/281026/0028206`, идентификатор `S116510021328` и отметки зарегистрированной декларации
- **THEN** эти значения не копируются в новую декларацию и не заменяются имитацией номера регистрации
- **AND** связь ДТ и ДТС задаётся техническим идентификатором текущего комплекта по допустимому правилу профиля

### Requirement: Offer exactly the agreed downloads
Четвёртая страница SHALL содержать две крупные синие кнопки «Скачать PDF» и «Скачать XML»; первая отдаёт PDF ДТ, вторая — ZIP ровно с двумя XML ДТ и ДТС текущей подтверждённой версии.

#### Scenario: Download both formats
- **WHEN** готовый комплект успешно проверен и пользователь нажимает кнопки скачивания
- **THEN** получает один PDF и ZIP с двумя читаемыми XML без документов других сессий, исходных файлов и дополнительного PDF ДТС
- **AND** скачивание повторно не вызывает Mistral и не изменяет содержание комплекта
