# Связи сущностей сопоставления граф

Графовый ответ AI использует контракт `graph-mapping-v2`. Каждое вложение сохраняет отдельный `fileId` из манифеста, в том числе повторная копия файла. После валидации сервер переводит `itemKey` и `recordKey` в backend ID, зависящие от сессии, и сохраняет связи в `graphMappingIdentity`. Срок хранения реестра совпадает со сроком жизни временной сессии.

Товары из последующих окон получают список `knownGoods`. Модель должна вернуть прежний key для той же строки товара; сервер не объединяет позиции по сходству наименования. `itemKey` последовательно переносится в результаты граф, факты ДТС, запросы справочников и связи юридических документов. Общие графы остаются с `itemKey=null`; их масса или количество мест не размножаются по товарам.

Юридические записи имеют независимый `recordKey`; модель получает подтверждённые ранее записи в `knownDocumentRecords` и повторно использует их key при обработке того же договора или приложения. Сервер также объединяет точные копии одного вложенного файла только когда совпали хеш файла, положение цитируемых фрагментов и типизированные значения. Записи разных страниц общего PDF не объединяются. Если проверить точную идентичность нельзя, создаётся отдельный record ID.

Факты ДТС-1-2 требуют явную `participantRole`. Реестр связывает роли с отдельными ID `party-seller`, `party-buyer`, `party-consignor`, `party-consignee`, `party-declarant` и `party-financial`. Эти связи не приравнивают seller/buyer к consignor/consignee.

Каждый шаг привязки готовит копию результата и реестра и возвращает их вместе; неполный вход отклоняется до выдачи изменений. Факты без точной ссылки на файл не участвуют в объединении по отпечатку, а остаются отдельными предложениями.

Проверяемые случаи находятся в `tests/php/GraphMappingIdentityLinkerTest.php`: повторное использование товаров в окнах для комплектов из 2 и 5 позиций, общие графы мест и отдельные массы, точные копии документов, договор с приложением в одном PDF и независимые роли ДТС.
