# Размещение на PS.kz XS / Plesk

Приложение подготовлено для PHP 8.3 и статического frontend. Проверка на фактическом аккаунте PS.kz ещё не выполнена. По опубликованным ограничениям XS предоставляет 1 ГБ SSD и 256 МБ памяти; число PHP/CGI-процессов сайта ограничено пятью. Эти пределы не доказывают доступность всех настроек в конкретной подписке. [Ограничения PS.kz](https://docs.ps.kz/ru/hosting/website-hosting/getting-started/hosting-limits).

## Подготовка релиза локально

1. Установить зависимости из lock-файлов: `composer install --no-dev --prefer-dist`, `npm ci`.
2. При обновлении `reference/TNVED/tnved.json` выполнить `php bin/build-tnved.php`. Выполнить проверки и `npm run build`. Весь каталог `resources/tnved/` (наименования, индекс кодов, контекст и 96 файлов тарифов) вместе с `resources/registry/catalogs.v1.json` должен попасть в размещение вместе со схемой/prompt; исходник `reference/` на хостинге не требуется. Подбор кода описан в [инструкции ТН ВЭД](tnved-selection.md).
3. Запустить `php bin/build-release.php`. Получится `release/customs-declaration-mvp.zip`, содержащий готовые `vendor/` и `public/assets-app/` и SHA-256 манифест файлов. Исходные документы, тесты, ключ и локальные инструменты исключены.
4. Распаковать этот архив в отдельный каталог или отдельный репозиторий/ветку размещения. В Git для хостинга должны попасть готовые `vendor/` и `public/assets-app/`. Если размещается текущая ветка проекта, после сборки включить новый JS-файл с hash в имени и обновлённый `index.html` вместе; наличие исходников React не заменяет готовый frontend.
5. Не добавлять `config/local.php` и временные файлы в Git. Секрет задаётся на хостинге отдельно.

Скрипт сборки не делает commit/push и не публикует сайт. Проверить перечень файлов перед загрузкой в свой Git.

## Настройка Plesk

1. В панели домена выбрать PHP 8.3 и HTTPS. Нужны curl, fileinfo, gd, mbstring, openssl, dom/libxml, xmlreader/xmlwriter, zip/zlib. Проверить доступность расширений и HTTPS-запросов к `api.mistral.ai`; наличие пункта PHP в панели само по себе этого не подтверждает.
2. Подключить подготовленный Git-репозиторий размещения. В официальной инструкции PS.kz описаны добавление удалённого репозитория и SSH deploy key: [подключение GitHub](https://docs.ps.kz/ru/hosting/website-hosting/control-panel/plesk-github-repository). Если используется локальный репозиторий Plesk — [соответствующая инструкция](https://docs.ps.kz/ru/hosting/website-hosting/control-panel/plesk-local-git).
3. Выбрать каталог размещения, например `httpdocs/customs`. Document root домена установить в `httpdocs/customs/public`. Корень проекта целиком публичным не делать.
4. Через файловый менеджер создать закрытые настройки и runtime вне `public` и вне заменяемых Git файлов, например `private/customs-config.php` и `private/customs-runtime`. Разрешить доступ только системному пользователю подписки. Для общей конфигурации web PHP и заданий добавить `config/local.php` вне Git с `return require '/фактический/путь/private/customs-config.php';`. Фактический путь нужно взять из панели, не копировать пример буквально.
5. В приватных настройках указать `mistral_api_key`, абсолютный `runtime_dir` и `secure_cookie=true`. Структуру взять из `config/local.example.php`; ключ не вставлять в браузерный JavaScript.
6. Настроить PHP: `memory_limit=192M` как стартовую проверенную локально границу; `upload_max_filesize=10M`, `post_max_size=12M` или больше, не выходя за лимиты тарифа. Один HTTP-запрос содержит один файл; ограничения сессии проверяет приложение. TLS-проверку cURL не отключать; при ошибках сертификата установить корректный CA bundle на стороне PHP.
7. Создать задания Plesk типа **Run a PHP script** для `bin/worker.php` и `bin/cleanup.php`, выбрать PHP 8.3 и начать с интервала раз в минуту, если он доступен. Выполнить **Run now** и проверить результат. Не использовать shell post-deploy-команды, постоянный процесс или публичный URL запуска worker. [Типы задач Plesk](https://doc.plesk.com/en-US/obsidian/administrator-guide/64993/), [выбор PHP для задания](https://support.plesk.com/hc/en-us/articles/12377377419287-How-to-run-a-PHP-script-using-a-custom-PHP-executable-in-Plesk-Scheduled-Tasks).
8. Для диагностики создать одноразовое задание PHP `bin/check-platform.php`. Оно выводит наличие расширений, память, возможность атомарной записи/блокировки и только признак настройки ключа, без самого ключа. Вывод задания доступен владельцу панели; диагностический HTTP endpoint не создаётся.

Настройки PHP домена могут отличаться от CLI-задания; проверить память, CA bundle и расширения отдельно для worker. Это ограничение Plesk описано в [официальной заметке](https://support.plesk.com/hc/en-us/articles/12377478114711-Plesk-scheduled-tasks-fail-due-to-domain-PHP-settings-not-taking-effect). Фактические максимальная длительность задач, допустимый интервал и исходящий HTTPS на XS должны быть проверены на аккаунте. Если нужного пункта нет в подписке, уточнить доступность у PS.kz; не заменять его незашищённым публичным запуском.

## Обновление параллельного OCR

Разместить обновлённые `src/`, `bin/worker.php` и собранный frontend; если UI собирается отдельно, учесть новый прогресс по файлам и продолжать polling, пока есть `queued`/`running`, даже при ошибке другого файла. Формат `/api/session` сохранён. Расписание worker и cleanup и приватный конфиг остаются прежними; дополнительные cron-задачи для каждого файла не нужны.

Проверить доступность `curl_multi_init`, `curl_multi_exec`, `curl_multi_select` в CLI PHP 8.3. Один worker отправляет до `max_files` OCR-запросов одновременно (20 по умолчанию), передаёт Base64 потоком, сохраняет каждый результат отдельно. После 150 секунд он перестаёт брать новые задания; уже запущенные запросы могут занять ещё до `http_timeout`. Лимит выполнения PHP/планировщика должен учитывать это время. Повторный запуск при активном worker вернёт `busy`. При 429 не увеличивать число cron-запусков: действует ограниченный повтор только неуспешных частей. Фактические ограничения аккаунта Mistral и PS.kz проверяются на размещении.

## Приёмка и откат

Проверить `/api/health`, загрузить оба набора первички в двух независимых браузерах, дождаться заданий, выбрать источники, заполнить обязательные данные и создать файлы. Проверить доступность ровно PDF и ZIP с двумя XML, неизменность повторного скачивания и отсутствие доступа между сессиями. После правки старые файлы должны стать недоступны. Срок сессии по умолчанию — два часа бездействия; подтвердить физическую очистку заданием без открытой страницы.

Зафиксировать время OCR/сопоставления/генерации, usage, peak memory и расход диска; локальные измерения не заменяют эти результаты. Учитывать интервалы cron при ожидании обработки.

Для отката выбрать прежний проверенный commit ветки размещения в Plesk и развернуть его готовые файлы. Приватные настройки и runtime не заменять из Git. При несовместимом изменении модели дождаться истечения активных сессий или явно завершить их перед переключением; архив деклараций не ведётся. Контрольные суммы позволяют проверить содержимое релиза.
