# Подбор ТН ВЭД, ставки и единицы товара

Исходник: `reference/TNVED/tnved.json`, предоставленный пользователем. Проверены 18014 уникальных записей, 13294 конечных десятизначных кода, 96 групп, непустые наименования и ссылки на существующих родителей. Промежуточные коды длиной 2/4/6/8/9 не подставляются в поле товара. Ведущие нули сохраняются строками.

## Подготовка и размещение

Локально выполнить `php bin/build-tnved.php` (в текущем окружении `.local-tools/php/php.exe bin/build-tnved.php`). Команда проверяет исходник и создаёт:

- `resources/tnved/catalog.v1.json` — наименования, иерархия, ссылки на PDF/страницы и hash исходного файла; около 10.2 МиБ.
- `resources/tnved/codes.v1.json` — небольшой индекс существования кодов.
- `resources/tnved/tariffs/*.json` — базовые формулы и единицы по 96 группам; runtime держит не более четырёх групп.
- `resources/tnved/tariff-context.v1.json` — покрытие, 25 единиц, 134 сноски и ссылки на источники без полных текстов страниц.

Команда также обновляет список дополнительных единиц в `resources/registry/catalogs.v1.json`.

В Git/релиз должны войти все runtime-файлы вместе с backend, схемой/prompt и собранным frontend. `bin/build-release.php` включает их через `resources/`. На PS.kz исходная папка `reference/` и повторная конвертация не нужны. При обновлении исходника индекс пересобирается локально; версия справочника входит в fingerprint сопоставления, успешный OCR не инвалидируется.

Полные тексты страниц исходных PDF не копируются в runtime; признаки покрытия и связанные сноски сохраняются. В текущей локальной проверке конвертация обновлённого файла использовала около 156 МиБ пиковой памяти, локальный поиск — около 28 МиБ; оба укладывались в настроенный лимит PHP 192M. Проверка существования кода использует отдельный небольшой индекс. Это локальные измерения, не проверка аккаунта PS.kz.

## Поведение формы

1. Код из документа извлекается с прежней проверкой точной цитаты и проверяется по списку конечных записей. Отсутствующий в справочнике код не становится достоверным автоматически; явная ручная корректировка остаётся доступной.
2. Если кода нет, после получения описания выполняется локальный поиск. Единственное точное совпадение полного короткого названия заполняет поле со статусом «Подобрано по справочнику». Например, «этилацетат» → `2915310000`.
3. Для английского названия существующий AI-вызов сопоставления может вернуть `classificationQueries`: исходное название, русский поисковый перевод и цитату первички. Backend проверяет источник и связь с текущим товаром/его кандидатом. AI не возвращает код для этого поиска; все коды берутся из локального JSON. Дополнительных OCR или отдельных AI-вызовов не добавляется.
4. Русское название не заменяется свободным AI-пересказом. Общее английское название вроде GLUE не позволяет автоматически выбрать специфический код только по расширенному переводу. Материал, состав, назначение и фасовка не достраиваются из бренда.
5. Несколько результатов остаются вариантами. Общее «клей» не выбирает автоматически `3506910000`: есть разные клеи, адгезивы и условия фасовки. UI показывает до 12 кодов с полными справочными наименованиями в источнике и общее число найденных позиций; ограничение отображения не делает первый вариант однозначным. Один приблизительный результат также не считается точным.
6. Пользователь может уточнить описание, выбрать вариант или ввести код вручную. Изменение описания обновляет автоматический подбор, ручной/выбранный код сохраняется. Несколько товаров обрабатываются независимо; повтор того же подбора не дублирует варианты. Название, версия справочника, исходные цитаты и PDF/страница справочника сохраняются в происхождении.
7. Выбранный код остаётся обычным `goods.commodityCode`: расчёт и подтверждение используют текущую ревизию, PDF и оба XML получают его из единого snapshot.

## Границы проверки

Дата `retrieved_at` — дата получения JSON, не дата вступления каждого кода в силу. `full_name` составлено из иерархии и не является самостоятельным официальным наименованием. Обновлённый JSON v2 включает базовые ставки и сноски, однако точное совпадение названия не доказывает юридическую классификацию состава товара. [Официальный раздел ЕЭК](https://eec.eaeunion.org/comission/department/catr/ett/), [основные правила интерпретации](https://eec.eaeunion.org/upload/files/catr/ett/%D0%9E%D0%9F%D0%98_%D1%81%D0%BE%D0%BA%D1%80%D0%B0%D1%89%D0%B5%D0%BD%D0%B8%D1%8F_%D0%B4%D0%BE%D0%BF.%D0%B5%D0%B4.%D0%B8%D0%B7%D0%BC.pdf).

Морфологический поиск выдаёт кандидатов: общего слова «болты» или «клей» недостаточно для выбора материала/размера/состава. После выбора кода заполняется связанный базовый тариф с отдельным подтверждением применимости. Свойства, отсутствующие в первичке, уточняются пользователем.

Автоматические проверки покрывают целостность каталога, ведущие нули, русское/английское название, неоднозначность и ограничение списка, неизвестные коды, ложные цитаты/переводы, независимость товаров, правки/повторы, происхождение, отсутствие дополнительных модельных запросов и совпадение кода в PDF/ДТ/ДТС. Новая схема запросов и качество перевода на реальном Mistral в этом изменении не проверялись платным прогоном.

## Ставки и единицы JSON v2 — 13.11.2026

Все 13294 конечных кода содержат `base_rule`, но `effective_rule`, `effective_from` и `effective_to` не заполнены. Покрытие явно исключает национальные исключения Казахстана/ВТО, преференции, НДС, акциз, сборы, специальные защитные платежи и валютные курсы. Автозаполнение не определяет эти значения и не объявляет базовую ставку действующей. Даты в сносках не считаются автоматически периодами применимости. [Официальная ЕТТ ЕЭК](https://eec.eaeunion.org/comission/department/catr/ett/) и [материалы КГД по ВТО](https://www.kgd.gov.kz/ru/section/vto?page=1) остаются источниками проверки применимости.

После выбора кода подставляются формула, операнды, ссылка/страница, сноски и дополнительные единицы. Например, 2915310000 даёт базовые 5%, без дополнительной единицы. Для новых справочных ставок нужны дата расчёта и явное подтверждение применимости пользователем. Смена кода, версии, даты, страны происхождения, льготы или параметров сбрасывает подтверждение. Расхождение с `base_rule` требует ручного основания. Уже введённые вручную ставки и их основания сохраняются; переключатель «Использовать ставку по ТН ВЭД» позволяет различать справочный и ручной ввод.

Поддержаны пять формул пошлины 2010: процент; сумма в валюте за количество единиц; `max(процент; специфическая)`; сумма этих компонентов; `min(процент; max(другой процент; специфическая))`. Расчёт использует точные рациональные числа, сравнивает неокруглённые компоненты и округляет окончательный платёж до двух знаков HalfUp. Специфическая часть: ставка × количество / количество единиц ставки × курс / номинал курса. Её валюта добавляется к обязательным курсам; дата, положительность и подтверждение проверяются как для инвойса. В НДС включается рассчитанная пошлина по существующему предварительному профилю; НДС и сборы по-прежнему вводятся отдельно.

Единица ставки и дополнительная единица отчётности различаются. Нетто для ставки в кг связано с `netMass`. Для совпадающих размеров можно связать штуки/100 штук/1000 штук и литры/1000 литров; пары не превращаются в штуки, литры чистого спирта — в литры продукта. При квалификаторе вроде «колоды» автоматического пересчёта нет. Для объёма двигателя требуется суммарное количество см³ по товарной группе. Никакие количества не вычисляются из одного кода или количества грузовых мест. В восьми кодах одновременно нужны две дополнительные единицы: оба количества обязательны. При смене единицы прежнее несовместимое количество очищается.

Расчёт и XML имеют разные границы. В согласованном образце XML нет специфических/комбинированных ставок и дополнительных единиц: эти случаи рассчитываются, но создание комплекта блокируется `XML_BRANCH_UNSUPPORTED` с адресами полей. Процентные случаи без неподдерживаемых веток экспортируются как раньше. Это сохранённое решение пользователя до получения XSD; совместимость с Keden не заявляется.
